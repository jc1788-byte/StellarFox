ISSUE #1: DETAILED HEALTH MONITORING ✅ COMPLETE
================================================================================

Problem: No separate liveness/readiness probes with dependency checks

Solution Implemented:
  • Liveness Probe: GET /healthz/live (always 200 if process alive)
  • Readiness Probe: GET /healthz/ready (200/503 based on dependencies)
  • Database Health Check: Verifies DB connectivity
  • RPC Health Check: Verifies RPC connectivity
  • Cursor Staleness Detection: 5-minute threshold
  • Dependency Status Tracking: Individual health for each dependency

Key Files:
  ✓ src/health.ts - Enhanced with dependency tracking
  ✓ src/db.ts - Added checkDatabaseHealth() function
  ✓ src/server.ts - Added health check endpoints

Benefits:
  • Kubernetes can properly detect live vs. ready services
  • Load balancers only route traffic to ready services
  • Detailed debugging info for infrastructure issues
  • Automatic restarts when dependencies fail

ISSUE #3: CHECKPOINT-BASED RECOVERY ✅ COMPLETE
================================================================================

Problem: Service restarts lose all progress, requiring full re-indexing

Solution Implemented:
  • Automatic Checkpointing: Creates snapshot every N events (default: 1000)
  • Persistent Storage: Saves to disk in ./checkpoints/ directory
  • Automatic Recovery: Resumes from last checkpoint on startup
  • Manual Recovery: Can recover to any historical checkpoint
  • Checkpoint Cleanup: Maintains only last N checkpoints (default: 10)
  • Data Preservation: Stores ledger sequence and paging token

Key Files:
  ✓ src/checkpointRecovery.ts - Checkpoint management (~350 lines)
  ✓ src/poller.ts - Checkpoint creation and recovery logic
  ✓ src/server.ts - Added /checkpoints/status endpoint

Endpoints:
  • GET /checkpoints/status - View checkpoint stats and recovery info

Configuration:
  • CHECKPOINT_INTERVAL_EVENTS=1000 (create checkpoint every N events)
  • MAX_CHECKPOINTS_TO_KEEP=10 (retain last N checkpoints)

Benefits:
  • Minimize data loss on failures (max loss = CHECKPOINT_INTERVAL_EVENTS)
  • Fast recovery without full re-indexing
  • Historical checkpoint access for manual recovery
  • Automatic cleanup to prevent disk space issues
  • Seamless resumption from failure point

ISSUE #4: EVENT FILTERING & SAMPLING ✅ COMPLETE
================================================================================

Problem: Processing/storing all events unnecessary, high costs

Solution Implemented:
  • Event Type Filtering: Whitelist/blacklist specific event types
  • Contract Filtering: Whitelist/blacklist specific contracts
  • Ledger Range Filtering: Include/exclude ledger sequences
  • Topic Filtering: Filter by event topics
  • Random Sampling: Keep random percentage of events
  • Systematic Sampling: Keep every Nth event
  • Adaptive Sampling: Auto-sample when queue depth exceeds threshold
  • Pre-configured Presets: invoices, markets, trades

Endpoints:

Features:

  • Multiple sampling strategies for different use cases
  • Automatic queue-based adaptive sampling
  • Pre-built filter presets for common scenarios
  • Estimated efficiency metrics

Benefits:
